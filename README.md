# Kairo ☀️

*Find a little time together.* An iPhone app, with an interactive Home Screen widget, that helps families across time zones find good times to talk.

> **Status: what is verified.** The logic package (`KairoCore`) builds and passes **48 tests** with Swift 6.3 on macOS.
> The SwiftUI app, WidgetKit extension, App Intents and Live Activity are written against that package but were **never compiled**: the authoring machine had Command Line Tools only (no Xcode, no iOS SDK, no Simulator). They were syntax-checked (`swiftc -parse`) and nothing more. Expect a few compile fixes on first build in Xcode. Nothing was run on a device. See [Validation](#validation).

**Privacy principle.** Availability learning uses communication *metadata* (call outcome and length, reply timing, Busy/Book taps), never message content. This describes the *availability model*, not the whole messaging service: a messaging/calling provider may process its own transport metadata, and an SMS bridge would process message bodies. See [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Setup (needs a Mac with Xcode 16+)

1. `brew install xcodegen && xcodegen generate && open Kairo.xcodeproj`
2. In `project.yml`, change `bundleIdPrefix`, set `DEVELOPMENT_TEAM`, and pick an App Group id.
   Put the **same** id in `Shared/AppGroup.swift` (`AppGroup.identifier`) and in both targets' App Groups capability.
3. Targets and capabilities (generated by `project.yml`, listed so you can verify):
   - **Kairo** (iOS app): App Groups; `NSSupportsLiveActivities = YES`; URL scheme `kairo`. Sources: `App/`, `Shared/`. Links `KairoCore`.
   - **KairoWidget** (Widget Extension): App Groups. Sources: `Widget/`, `Shared/`. Links `KairoCore`.
   - No Contacts, Microphone, Push, or Focus capabilities are needed for this milestone.
4. Run the **Kairo** scheme on an iPhone simulator or device (iOS 17+), long-press the Home Screen, add the **Kairo** widget (medium is the hero).
5. If the App Group isn't configured, the app still runs and says so; widgets show an honest "shared data unavailable" state.

Run just the logic tests anywhere with Swift 6 (also works in Xcode with `⌘U`):

```bash
swift test
```

On a Mac with only Command Line Tools, Swift Testing needs framework paths:

```bash
F=/Library/Developer/CommandLineTools/Library/Developer/Frameworks
swift test -Xswiftc -F$F -Xlinker -F$F -Xlinker -rpath -Xlinker $F \
  -Xlinker -rpath -Xlinker /Library/Developer/CommandLineTools/Library/Developer/usr/lib
```

## Two-minute demo

The demo clock starts at a fixed instant: **Sun 8 Nov 2026, 7:12 PM in Durham = 9:12 AM in Seoul = 3:12 AM in Addis Ababa**, and keeps running. Onboarding → **Try demo family**.

1. **Family** tab: Durham/Seoul/Addis local times from one instant; Sis shows *Quiet hours* (from her preferences, not an inference of sleep).
2. Tap **Mom** → weekly heatmap built from the synthetic history (labeled synthetic everywhere), plus an estimate explanation.
3. Three suggested windows are shown; each has a short deterministic explanation.
4. **Book this time** on one → "Waiting for Mom" (persisted; widget shows it after reload).
5. **Settings → Demo controls → Acting as → Mom**, then **Confirm** (or use "Confirm as Mom"). The state becomes **Booked**.
6. Return to the app: the Live Activity starts if the call is within an hour (see limits below); otherwise a note explains why not yet.
7. **Demo controls → Advance to call time**, then **Open call** → in-app *simulated* call screen (or FaceTime audio if you entered your own destination in Settings).
8. Back in the app: **Did you connect? Yes / No / Skip**, which is self-reported, not telemetry.

Closing line: *"Kairo learns when you tend to connect, without using what you say to predict your availability."*

## Honest limits (read before demoing)

- **Widgets**: refreshes are system-controlled. The timeline pre-computes 30-minute entries from a cached snapshot, but iOS may reload less often. Widgets never wait on the network. Countdown text uses system timer rendering; nothing runs second by second.
- **Interactive buttons**: Book/Busy are real App Intent buttons (iOS 17). *Call* and navigation are deep links.
- **Live Activity**: cannot be started from the widget button's process. Booking from the widget sets `pendingLiveActivityProposalID`; the app starts the activity when next foregrounded and only within 60 minutes of the call (activities can't last days). Farther-out calls get a local notification (asked for only when first needed). Disabled-activities and failure cases show a note; the booking is unaffected. ActivityKit *push* updates and PushKit *VoIP* pushes are different mechanisms; neither is used here.
- **Calls**: FaceTime audio only if *you* enter a destination; otherwise a labeled simulation. The app cannot observe whether a FaceTime call connected or its length.
- **Estimates**: scores rank slots; they are not calibrated probabilities. See the formula and limits in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Validation

Run on 7 Nov 2026, Apple Swift 6.3.3, macOS (Command Line Tools):

- `swift build`: **passed**
- `swift test`: **48 tests in 7 suites passed**: time zones & DST (spring-forward gap, fall-back repeat), different local dates, quiet hours across midnight, low-confidence "Learning", Busy precedence/expiry, fairness ranking, two-participant confirmation, duplicate and concurrent confirmations, expired/stale proposals, shared-cache encode/fallbacks, agent consent and validation, summary privacy
- `swiftc -parse` over all `App/`, `Shared/`, `Widget/` files: **no syntax errors**

**Not checked:** Xcode build, type-checking against the iOS SDK, any Simulator or device run, widget rendering, App Intent execution, Live Activity/Dynamic Island, push delivery, incoming calls, the Supabase SQL (not run against Postgres), the Deno function (Deno not installed), and the XcodeGen spec. Widget previews exist but were not rendered.
